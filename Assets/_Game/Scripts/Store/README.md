# Store sample

The Week 10 Lab A screenshot capture. `StoreShot.cs` hides what must not be in a store screenshot, waits one frame, captures with `ScreenCapture.CaptureScreenshot` at the screen's size (or a multiple, `superSize`), waits until the file is on disk, and shows everything again; it logs `[Shot] Saved <path>`. Files land in `Application.persistentDataPath` as `Scene_NN_WxH.png`; pull them with `adb pull /sdcard/Android/data/com.dftgames.mgdsamples/files/`. Copy it, and put your HUD root in `hideWhileCapturing`. The test is `StoreShotTests` in `Assets/_Game/Editor/Tests/`.

It differs from the deck's version mainly in four ways. The Launcher creates it once on a DontDestroyOnLoad object with its own small canvas, so the Shot button is there in every scene; the button shows in Development Builds only, as the deck's `DebugShotButton` does, so there is no separate script. The lab removes both scripts in Week 12; here release builds keep the object with the button switched off. In a game the HUD is hidden and the gameplay remains, but in this app the UI is the content, so the only thing hidden is the Shot button's own canvas (`hideWhileCapturing` is a list, where the deck has one `hudRoot`). It deletes an older file of the same name, then waits until the new file is complete, in real time, rather than for 0.5 s of game time, which never passes while the game is paused. And the file name carries a shot number, `Scene_NN_WxH.png`, and the log line reads `[Shot] Saved`, where the lab's troubleshooting says `Saved ...`.

A Development Build stamps "Development Build" in the bottom-right corner, and the capture includes it; `docs/store/asset-checklist.md` shows how the worked screenshots dealt with that and with the phone's 20:9 screen. The store kit itself (icon, feature graphic, screenshots, descriptions, critique notes) is in `docs/store/`. Design notes are in the `MGD_MODULE_GDD` vault, note `Samples/Store`.
