# QA sample

The Week 8 Lab B failure signatures, made on purpose so each one is seen once before it turns up for real. Start a logcat recording first (`adb logcat -c`, then `adb logcat -v time > qa.txt`), then:

- **Throw exception:** a `Unity` line with `InvalidOperationException: [QA] Deliberate exception from the QA scene.` and its stack (search for `InvalidOperationException`: logcat pads the tag with spaces). Unity logs it and the app carries on, as it would after a real bug in a handler.
- **Freeze UI thread (ANR):** blocks Android's UI thread for 10 s. Tap an empty part of the screen straight away (within 5 s, because Android's input timeout is 5 s from the tap); 5 s after the tap logcat shows `ActivityManager: ANR in com.dftgames.mgdsamples` with `Input dispatching timed out`, and Android offers to close the app. Choose *Wait*: the app recovers when the freeze ends, with the pause panel up (the dialog took focus), so press Resume. Presses of the ANR button made during the freeze are ignored, so they cannot start a second one. Unity runs the game on its own thread, not on Android's UI thread, so a `Thread.Sleep` in a button handler only freezes the game; the button uses `AndroidApplication.InvokeOnUIThread` to block the thread Android watches.
- **Native crash:** `Utils.ForceCrash(ForcedCrashCategory.AccessViolation)`: Unity's `CRASH` lines, then `libc : Fatal signal 11 (SIGSEGV)`, then the tombstone under the `DEBUG` tag. The app is gone; relaunch it.

Each button needs a second tap within 3 s (`ArmedTrigger.cs`), because the app really freezes or dies. In the editor the ANR and the crash only log, so they cannot take the editor down. `QaTriggers.cs` also counts `Application.lowMemory` and logs `[QA] lowMemory #n`: Unity raises it for `onLowMemory` and for `TRIM_MEMORY_RUNNING_CRITICAL`, which is what Lab B's `adb shell am send-trim-memory com.dftgames.mgdsamples RUNNING_CRITICAL` sends. Android 14 (API 34) and later no longer send apps the `RUNNING_*` trim levels, so on most current phones the count stays at 0 after `send-trim-memory ... RUNNING_CRITICAL`; that is the expected result, not a bug, and a game that must shed memory reacts to its own budget or to `TRIM_MEMORY_UI_HIDDEN` and `BACKGROUND` instead. Copy `ArmedTrigger.cs` for any button that cannot be undone; the triggers themselves are teaching scaffolding, and your own game should not ship them. The test plan this feeds is `docs/qa/test-plan.md`. Design notes are in the `MGD_MODULE_GDD` vault, note `Samples/QA`.
